## Domain state, admission, and fences

The Letfs schema/controller groundwork must already be ported off operations in phase 5. This phase completes processing behavior and consumers against that model.

Keep current business readiness on the original file's files row: desired processing generation/source content identity, current attempt fence when needed, published generation/artifact-root reference, indexed generation, publication_status, index_status, a persisted vector-space identity (embedding model, collection and dimension), and a bounded user-visible failure code. Choose native precise field types during phase-5 schema work. These fields replace existing invariants rather than inventing new workflow history.

- These are serving/publication facts, not Temporal running/retrying/stage history. Do not add a generic processing_runs/stages/attempts database hierarchy.
- Change desired generation and invalidate obsolete publication/index readiness atomically with the source mutation. Use content identity/version, not an unrelated rename revision alone, for byte-dependent fencing.
- Record sufficient durable intent to dispatch ProcessFile after commit. Use phase-4 start/reconciliation rules and stable workflow identity derived from file + generation.
- Manual reprocessing REQUIRES a caller-scoped Idempotency-Key. Atomically bind its normalized file/source identity and request to the admitted generation/workflow handle in Letfs idempotency_keys. Same-key retry returns that handle; changed input conflicts. Commit-before-response loss must not request another generation or repeat model costs. Apply the common 24h-after-logical-completion retention policy.
- Each processing attempt has an accepted fence and stable output identities. Validate file scope, generation, content identity, current attempt and ancestor lifecycle at every publication/ready boundary.
- A stale attempt cannot publish metadata, overwrite a newer root, make a deleted file searchable, or mark the latest generation ready.
- Do not rely solely on Temporal cancellation to stop stale external calls. Database compare-and-set and generation-specific remote identities enforce correctness.
- Source trash/replace/delete and parent deletion supersede pending work and make obsolete uploads/artifacts eligible for the existing cleanup owners. Preserve artifact readonly and hybrid ID/path/cwd semantics.
- Keep only the current domain state needed by serving. Temporal retains execution diagnostics/history; the API documents history-retention limits.

GET nodes/{id}/processing exposes current publication/index readiness. POST nodes/{id}/processing-runs requests reprocessing but does not imply a new SQL run table. Internal processor resources should expose only actual cross-service boundaries: accepted output identity, publication result, and index readiness. Local Rust Activity-to-domain calls do not need HTTP endpoints.

## Shared artifact transport and publication

1. Letfs admits a file generation and returns a stable accepted source/attempt/output context to the workflow/processor.
2. Python parses source bytes with the real parser and produces bounded output descriptors and bytes. Do not place file bytes or full model prompts in Temporal history.
3. Python uploads generated bytes using the same Letfs uploads transport as user clients. Stable keys use file + generation + logical output path/identity; retries resolve existing finalized sessions instead of creating unlimited sessions.
4. Upload finalization proves transfer completion only. Unpublished processor bytes remain associated with their accepted generation/output until Letfs validates publication.
5. Publish nodes/files metadata only after verifying required outputs and active generation. Retain the existing configured artifact/output count/byte/depth ceilings so a bounded publication transaction is meaningful.
6. Connect the artifact root and update original-file semantic/readiness facts in the correct publication transaction. Enqueue superseded objects/forests transactionally where applicable.
7. A response lost after publication resolves to the committed publication; it must not create another artifact tree or charge quota again.
8. Failed/superseded output bytes are cleaned via uploads/object_deletions and existing artifact-forest cleanup, preserving late-write evidence. No processing-specific duplicate upload transport or orphan memory-only list.

Model/provider failures remain explicit. Keep current supported parser formats and quality guarantees. Use the previous real-file evaluation reports as regression evidence; do not silently convert this refactor into a general parser rewrite or claim model quality from stubbed responses.

## Correct semantic ownership and order

1. Enrich actual leaf FILES from their own content.
2. For each artifact directory, generate/enrich its README.md directly from child file information and child READMEs, after its children are ready.
3. Continue upward to the artifact-root README.md.
4. Copy root README semantic metadata onto the original file's files row after the generation fence succeeds.

Directories themselves never receive title/description/semantic_type/context or MIME. Remove the old describe-folder/root then copy-to-README path. Original metadata must not be copied downward into root README and used as if it were new enrichment evidence.

Folder naming/title/slug derivation reads the folder README result where the existing pipeline needs it. Update readme.py/final-path derivation and downstream readers so no hidden directory-metadata dependency remains. Preserve path safety, deterministic collision handling, and existing output limits.

MIME is independent from semantic classification. The original-file metadata copy is an intentional serving denormalization from its published root README, not a second independent classification.

## Two worker processes, one Python application

| Process | Queue responsibility | Startup/dependency policy |
|---------|----------------------|---------------------------|
| CPU worker | Parsing, document extraction/OCR and other existing CPU-heavy conversion | Own bounded process/activity concurrency; load required parser models |
| I/O worker | LLM enrichment, embeddings and index/network work | Async bounded concurrency and provider timeouts; does not load parser/OCR prerequisites |

Keep a single apps/letfs-processing package/image unless the existing build proves a real need for separate images. Expose explicit process commands/roles and separate task queues. Do not split parsing/enrichment/indexing into additional microservices.

- Rust ProcessFile routes each Activity to the appropriate queue and uses the right timeout/heartbeat/cancellation policy.
- Do not register CPU parsing on the I/O worker or block its startup on Docling/OCR/model preflight.
- Reuse existing subprocess cancellation/reaping and output-limit protections; queue separation must not orphan parser children.
- Set bounded CPU/process and async I/O concurrency explicitly from actual capacity. Do not add an autoscaler or a general capacity scheduler.
- Both processes initialize the same phase-3 OTel integration with worker-role attributes and distinct process lifecycle. Traces propagate into both queues; no framework-specific telemetry payloads.
- Compose health/readiness and shutdown cover both roles. Verify no duplicate worker processes or stale old queue consumers remain.

## Versioned indexing and serving

Use generation-specific immutable Qdrant point identities/payloads and an explicit readiness compare-and-set:

1. Write chunks/embeddings for the accepted file generation. Repeated indexing of that same generation is idempotent.
2. Old generation writes cannot overwrite current generation point IDs.
3. Mark indexed_generation/index_status ready only if the file still desires the same generation and it is the published generation.
4. Search validates candidate filesystem/authorization, current file liveness, and published/indexed generation before returning results. Do not trust Qdrant payloads as authorization or current-version truth.
5. Cleanup deletes only superseded-generation points; a stale cleanup filter must not delete the newest generation. Use existing maintenance/reconciliation rather than a new broker/job table.
6. Handle late obsolete writes through generation filtering plus bounded reconciliation. Do not mark index-ready before remote acknowledgment or pretend SQL/Qdrant is one transaction.

### Durable index cleanup and vector-space identity

Source supersession, permanent deletion and collection changes enqueue index_deletions in the SAME database transaction as invalidating/removing serving metadata. This minimal domain outbox stores collection, source file, generation and vector-space identity, with an eligibility timestamp; it survives deletion of nodes/files. It is not a job/stage table and contains no execution history. Existing maintenance retries generation-scoped Qdrant deletion and retains intent while an old producer may still write. A terminal producer plus acknowledged final deletion permits pruning; a timeout with uncertain remote writes retains evidence for another reconciliation pass. Do not replace durable intent with an in-memory list or assume the deleted file row remains available.

Readiness is for BOTH a published generation and its exact vector space. Persist/compare model, collection and dimension (or an equivalent canonical identity), reject completion under a changed space, and make search reject old-space candidates immediately. On supported configuration change, invalidate indexed readiness and admit index-only work for the current published generation; do not rerun parsing/enrichment unnecessarily. Include the space identity in point identity and cleanup filters so old collection/model cleanup cannot remove newly indexed results.

Preserve supported search semantics and bounded queries. Do not add caching, new ranking providers, embedding dimensions, or benchmarks without a demonstrated need. Model/API stubs prove protocol/flow, while opt-in real-provider smoke proves only the provider behavior actually observed.

Basic filename search remains an SQL path independent of AI publication/index readiness. A fresh, pending or processing-failed file must still be discoverable by name when the caller can access it; only semantic/vector-derived results require the appropriate generation/vector-space readiness gates.

## Risks, recovery, and completion

Keep publication and index readiness separate: uploaded bytes, published nodes and searchable content are different milestones. SQL and Qdrant cannot be committed atomically; immutable generations and serving-time validation must close that gap.

Recover via coordinated code/config/database/object checkpoint restore after backup, not by reintroducing old migrations or compatibility paths. Clean only processes/containers created by the execution session. Do not commit/push/deploy unless separately requested.

Mark the plan complete only after every required gate has evidence. Record material remaining provider/environment limits beside the affected claim rather than silently dropping scope.
